# Data quality

Daily reports are typed by people under time pressure and generated by forms with quirks. This
document lists what WellScope checks, how findings reach users, and the kinds of anomaly found
in the sample data (described generically; the data itself is not reproduced).

## Principles

1. **Never correct a source value.** Every field keeps the raw text from the PDF next to any
   parsed value; a suspected error is reported, not fixed.
2. **Say what is uncertain.** When two reports disagree, answers give both values with their
   citations and a caveat. A blank field is reported as "not recorded", not guessed.
3. **Make checks visible.** Findings are written to `quality_report.json`, shown as badges in
   the report list, and given to the model as passages so answers can mention them.

## Checks

| Check | Applies to | What it verifies | Severity when it fails |
|---|---|---|---|
| `report.identity` | All reports | Report number and date were found | warning |
| `pdf.visibility` | All PDFs | The visible share of characters on every page is plausible (a very low share means hidden layers dominated) | warning |
| `operations.hours_total` | DDR | The operations table covers exactly 24.00 hours | warning |
| `operations.npt_matches_header` | DDR | Hours of rows flagged as non-productive time equal the daily NPT in the header | warning |
| `operations.row_hours` | DDR | Each row's hours match its time range | warning |
| `dates.spud_before_report` | DDR, DGOS | The spud date is not after the report date | warning |
| `dates.bop_test_order` | DDR | The next BOP test is not due before the last BOP test | warning |
| `conflict.*` | Across reports | The same fact (for example the spud date) has the same value in every report | warning |

The operations checks also guard the parser: the 24-hour total exposed two layout bugs during
development (see [RESOLUTION.md](RESOLUTION.md) #3).

## Where findings show up

- `data/processed/quality_report.json`: per report, the failed checks; across reports, every
  conflict with the value each report gives.
- `manifest.json` and the report list in the web app: a quality status per report (`ok` or
  `warning`, with a "notes" badge).
- The answer context: each report's data-quality notes are a passage, and conflicts involving
  the reports in question are added as their own source, so an answer about an affected value
  carries a caveat.

## Anomalies found in the sample data

| Kind | Description | Handling |
|---|---|---|
| Conflicting dates | A key date carries a different year in one report family than in the other; other fields support one of the two | Both values cited; a caveat explains the conflict |
| Illogical order | A "next test due" date falls before the "last test" date in the same report | Value quoted as written; quality warning |
| Header versus narrative | A header depth differs from the depth reached in the day's narrative (a pilot hole drilled deeper explains it) | Both values available with their context |
| Rounding | The same depth appears with different rounding in two report families | Each value cited with its source |
| Names | The operator named in the glossary differs from the name printed in the reports | Each source quoted for its own value |
| Typos in the source | Misspelled words and a wrong unit abbreviation in the reports | Quoted verbatim; the glossary documents the unit typo; search tolerates the misspelling |
| Unknown terms | A unit label and a field value that the glossary marks as unknown, a phase code not in the glossary | Answers say the meaning is unknown or not defined |
| Naming drift | The same logging run is named differently in two reports | Each name cited with its source |
| Text hidden in the PDF | Invisible text layers and labels covered by shapes | Removed by the visibility filter; the visible share is recorded |
| Text clipped by the form | Long values cut at a cell border on the page but complete in the file | The complete value is kept with its own cell |
